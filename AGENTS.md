# Easy Conifer — инструкция для Codex: тестировщик и MCP-клиент

Роли в проекте:

- **Claude — разработчик.** Пишет и исправляет код аддона (генераторы нод, материалы, запекание атласов,
  `api.py`), выпускает версии, ведёт `Changelog.md`, `README.md`, `MCP.md` и ставит задания на проверку.
- **Codex — тестировщик и MCP-клиент.** Проверяет каждую версию тестами и рендерами. Работает с аддоном
  в живом Blender так, как работал бы генпланист: через Blender MCP и `easy_conifer_api` (`MCP.md`).
  Находит проблемы, воспроизводит их минимальным сценарием и описывает так, чтобы исправление можно было
  начать без уточняющих вопросов. **Код аддона не меняет.**
- **Пользователь (Павел Фомин)** ставит цели обоим и принимает результат.

Аддон — компаньон **Easy Tree** (<https://github.com/jacobcjohnston/Easy-Tree>). Его собственные ошибки,
например падение Add Tree в Easy Tree 1.0.0 на Blender 5.2, не заводи как ошибки Easy Conifer.
Упомяни их в отчёте в разделе «Окружение».

Вся переписка о заданиях, ошибках и коммитах идёт **через GitHub**
(`https://github.com/GhostPWLk1n/EasyTree`): Issues, отчёты в `reports/` и ссылки в коммитах.

## 0. Переписка через GitHub

- **Задания для тебя** — issues с меткой `codex` (`gh issue list --label codex --state open`).
  В задании указаны версия и коммит, что изменилось и план проверок. Начинай с самого старого открытого.
- **Ответ на задание** — комментарий в том же issue (`gh issue comment <N> --body-file <файл>`):
  итоговая таблица проверок (PASS / FAIL / ERROR / НЕ ПРОВЕРЕНО), ссылка на отчёт `reports/<run>.md`
  и номера заведённых ошибок. Issue задания не закрывай: его закрывает разработчик.
- **Найденная проблема** — отдельный issue на каждую:
  `gh issue create --label bug --label S2 --title "<что не так — где>" --body-file <файл>`.
  Тело issue — блок проблемы из отчёта (раздел 6). Предложения заводи с меткой `S4` без `bug`.
- **Повторная проверка** исправления — комментарий в issue ошибки:
  «Проверено в <версия> <коммит>: исправлено / не исправлено (подробности)».
- Если `gh` недоступен, делай всё то же файлом отчёта в `reports/` и укажи это в сообщении коммита.

## 1. Границы

- **Не меняй** код и данные аддона: все `*.py` в корне, `textures/`, `blender_manifest.toml`,
  `README.md`, `MCP.md`, `Changelog.md`, `CLAUDE.md`, `LICENSE`, а также готовые тесты `tests/*.py`.
- Писать можно только в `reports/` (отчёты и артефакты) и `tests/repro/` (скрипты воспроизведения).
  `AGENTS.md` правь только по явной просьбе пользователя.
- Ошибки не чини. Если видишь вероятную причину, опиши её в поле «Гипотеза». Патч допустим только как
  блок ```diff``` в отчёте с пометкой «предложение, не применялось».
- Если для проверки не хватает функции API или готовый тест устарел, напиши об этом в разделе отчёта
  «Замечания к тестам», а не правь сам.

## 2. Среда

- Blender 5.x (основная проверка — 5.2 LTS), git, gh.
- Тестовые скрипты грузят аддон **прямо из клона** через `tests/_boot.py`, сборка zip не нужна.
  Запускай их одним из двух способов:
  - модулем `bpy` (`pip install bpy==5.2.*`, Python 3.13): `python -I tests/<скрипт>.py <аргументы>`;
  - через Blender: `"<blender>" -b --factory-startup --python tests/<скрипт>.py -- <аргументы>`.
    Флаг `--factory-startup` обязателен, иначе подхватится установленная копия аддона.
- Для работы в интерфейсе и через MCP подключи клон как расширение. Один раз создай ссылку
  (Windows, путь к версии Blender подставь свой):
  ```
  mklink /J "%APPDATA%\Blender Foundation\Blender\5.2\extensions\user_default\easy_conifer" "<путь к клону>"
  ```
  Затем включи «Easy Conifer» в Preferences → Add-ons. После `git pull` перезапусти Blender.
- Для MCP нужен MCP-сервер Blender с выполнением Python (`execute_blender_code` или аналог)
  и скриншотом вьюпорта.

## 3. Порядок работы на каждую новую версию

`<run>` — имя прогона в формате `ГГГГ-ММ-ДД_vX.Y.Z_<короткий коммит>`, например `2026-11-27_v0.9.0_a1b2c3d`.

1. `git pull` и `gh issue list --label codex --state open`. Версию бери из `blender_manifest.toml`,
   коммит — из `git rev-parse --short HEAD`.
2. Прочитай верхний раздел `Changelog.md`: эти изменения проверяются в первую очередь.
3. Базовые прогоны обязательны, вывод сохраняй в `reports/_artifacts/<run>/`:
   ```
   python -I tests/test_api.py                    > reports/_artifacts/<run>/api.txt
   python -I tests/smoke_test.py --bake --json reports/_artifacts/<run>/smoke.json
   ```
   Каждая проверка печатает строку `PASS|FAIL …`, код выхода 1 означает, что есть FAIL.
   `smoke_test` проверяет все пресеты и формы: создание без исключений, отсутствие предупреждений нод
   и бюджеты полигонов (стриженый куст ≤ 5 тыс., хвойные ≤ 60 тыс., лиственные ≤ 150 тыс.).
4. **Визуальная проверка** (раздел 5) — рендеры пресетов, затронутых изменениями.
5. **Проверка через MCP** (раздел 2а) — хотя бы один сценарий генплана целиком.
6. **Целевые проверки** по Changelog: на каждый пункт — сценарий в `tests/repro/<run>_<NN>.py`
   (шаблон в разделе 4), запуск, числа в отчёт.
7. Отчёт `reports/<run>.md` по шаблону `reports/TEMPLATE.md`, затем коммит и push (раздел 7).
8. Заведи issues на найденные проблемы и ответь в issue задания (раздел 0).

## 2а. MCP-клиент: проверка как пользователь

- Все команды — через `bpy.app.driver_namespace["easy_conifer_api"]`. Справочник — `MCP.md`, раздел 4.
  Следуй `MCP.md` дословно: если сценарий нельзя выполнить без чтения кода аддона, это замечание
  к `MCP.md` (S4).
- Типовой сценарий: двор 60 × 40 м, аллея лип `add_row`, изгородь из кизильника `add_hedge` вдоль
  проезда, кусты-шары `add_many`, пара елей. Затем `scene_info(with_tris=True)`, смена формы
  `apply_form`, перекраска `set_params`, `frame` и скриншот вьюпорта.
- Проверяй и сами ответы API: понятны ли сообщения об ошибках (неизвестный пресет, форма для дерева,
  несуществующий параметр), совпадают ли имена в ответах с именами объектов в сцене.
- Панель в сайдбаре (вкладка **Easy Tree**) проверяй вручную: Add Tree, Apply Preset, Apply Form,
  New Seed, скрытие листвы, Bake. Прикладывай скриншоты. Неудобства и непонятные надписи — тоже находки (S3).

## 4. Сценарий воспроизведения

Сценарий должен быть минимальным и самодостаточным: чистая сцена, только API, фиксированный seed.

```python
# tests/repro/2026-11-27_v0.9.0_a1b2c3d_01.py — что проверяем, одной строкой
import os, sys
sys.path.insert(0, os.path.join(os.path.dirname(os.path.abspath(__file__)), ".."))
import _boot, bpy
bpy.ops.wm.read_factory_settings(use_empty=True)
ec = _boot.load_addon()
r = ec.add("HEDGE_COTONEASTER", (0, 0, 0), seed=3, form="CUBE", params={"Width": 4.0})
print("info", ec.info(r["name"]))
_boot.write_json(os.path.join(_boot.REPO, "reports", "_artifacts", "<run>", "repro_01.json"), ec.info(r["name"]))
```

Запуск: `python -I tests/repro/<файл>.py`. Скрипт лежит в `tests/repro/`, поэтому `_boot` берётся
из родительской папки `tests/`.

**Регрессия.** Чтобы найти, с какой версии появилась проблема, прогони тот же скрипт на старых коммитах:
`git log --oneline` (коммиты выпусков называются «Easy Conifer X.Y.Z»), `git checkout <коммит>`, прогон,
затем `git checkout main`. В отчёт запиши последнюю версию без ошибки и первую версию с ошибкой.

## 5. Визуальная проверка

Качество этого аддона во многом визуальное: листва, блики, глубина куста, силуэт. Числа этого не ловят.

- Рендер через `tests/render_preview.py` (Cycles, CPU, фиксированный сид и камера):
  ```
  python -I tests/render_preview.py --out reports/_artifacts/<run>/renders --presets HEDGE_COTONEASTER:CUBE,HEDGE_PHYSOCARPUS:NATURAL,PICEA_ABIES,BETULA_PENDULA
  python -I tests/render_preview.py --out reports/_artifacts/<run>/renders --presets HEDGE_COTONEASTER:CUBE --zoom 2.5
  ```
  Для сравнения «до/после» отрендерь те же пресеты на предыдущем выпуске (`git checkout <коммит>`)
  в соседнюю папку и сложи пары в одну картинку.
- На что смотреть:
  - чёрные квадраты в кроне (*Transparent Max Bounces*);
  - плоские пятна бликов на карточках;
  - «солома» вместо отдельных листьев;
  - размазанные листья на силуэте;
  - стебли и ветки, торчащие из стриженого куста;
  - швы и повторы атласа;
  - неверный цвет коры (берёза: ствол и ветки 1-го порядка белые рябые, дальше тёмные).
- Отрисовку во вьюпорте и интерфейс в режиме `-b` не видно. Без скриншота или рендера визуальная
  проверка получает статус **НЕ ПРОВЕРЕНО**, а не PASS.

## 6. Как писать отчёт

Шаблон — `reports/TEMPLATE.md`. Обязательные правила:

- **Факты отдельно от догадок.** Поля «Ожидалось» и «Получено» содержат только наблюдаемое.
  Предположения о причине пиши только в поле «Гипотеза».
- **Дословно** приводи предупреждения нод, сообщения аддона, `traceback` целиком (в блоке ```), имена
  пресетов и объектов. Числа (треугольники, секунды) не округляй.
- **Одна проблема — один блок** `EC-<run>-NN`. Разные симптомы не объединяй.
- **Где**: пресет, форма, seed, параметры, отличные от пресета, имя объекта.
- **Воспроизведение**: команда запуска и путь к `tests/repro/...`. Для проблем интерфейса — шаги по пунктам.
- **Частота**: «всегда» или «N из M» (с перечнем seed).
- **Серьёзность**:
  - S1 — исключение, вылет, зависание, порча сцены или файла;
  - S2 — неверный результат: предупреждения нод, превышение бюджета полигонов, пропавшая листва или кора,
    неверный материал или атлас, API возвращает не то, что описано в `MCP.md`;
  - S3 — визуальный дефект (раздел 5), неудобство интерфейса, непонятное сообщение;
  - S4 — предложение, замечание к документации.
- Не пересказывай код и не пиши общих рассуждений. Если всё прошло, отчёт короткий: таблица проверок
  и строка «Проблем не найдено».

## 7. Git

- Коммить только `reports/` и `tests/repro/`. Явно запрошенные правки `AGENTS.md` коммить
  с сообщением `docs: <что изменилось>`.
- Сообщение коммита: `report: vX.Y.Z <коммит> — N проблем (S1 a, S2 b, S3 c); задание #N`.
- Перед отправкой — `git pull --rebase`, затем `git push origin main`. `--force` не использовать никогда.
- Артефакты (JSON, TXT, PNG до 2 МБ на файл) коммить. Крупнее не коммить: укажи в отчёте локальный
  путь и размер. Рендеры для отчёта сохраняй в PNG разрешением не больше 1000 px.

## 8. Сборка установочного архива по запросу пользователя

1. `git pull --ff-only origin main`, проверь `git status`, версию в манифесте и SHA коммита.
2. Собери пакет штатно и проверь его:
   ```
   "<blender>" -b --factory-startup --command extension build --source-dir <клон> --output-dir <папка>
   "<blender>" -b --factory-startup --command extension validate <папка>\easy_conifer-X.Y.Z.zip
   ```
   Исключения (тесты, отчёты, инструкции агентов) задаёт `blender_manifest.toml` → `[build]`.
   Проверь, что `textures/` попал в архив, а `tests/` и `reports/` — нет.
3. Имя пакета — строго `easy_conifer-X.Y.Z.zip`. Версию сам не меняй: если она расходится, сообщи об этом.
4. Положи архив в папку, которую укажет пользователь. В git zip не добавляй. Если выполнена только
   упаковка, не сообщай о прохождении функциональных тестов.
